How YOLO sees a road

Seven animations, each followed by the explanation of what it shows. The animations only show how things behave; the reasoning is in the text underneath.

1One look versus many

What you see

Left: a window checks one region at a time and a counter climbs. Right: the whole image is processed once, a grid appears, and every vehicle is boxed together.

The idea

YOLO stands for “You Only Look Once”. Older two-stage detectors proposed thousands of candidate regions and classified each one separately, which is accurate but slow. YOLO treats detection as a single regression problem: one forward pass of one network returns every box, class and confidence. It is fast enough for video and sees global context, so background is less likely to be mistaken for a vehicle.

In your project

RoadVision AI works on traffic cameras, so speed per frame matters. This is why YOLOv9-C was chosen for the prototype.

2An annotation is five numbers

class   x_center   y_center   width   height

What you see

Pick a vehicle. The box moves onto it and the five numbers update live.

The idea

Each line of a YOLO label file describes one object: a class id, then the box centre, width and height, all divided by the image size so they fall between 0 and 1. The class id comes from the order of names in data.yaml, so a mismatch there silently teaches the model wrong labels. Every vehicle needs its own line; an unlabelled vehicle teaches the model that it is background.

In your project

Step 2 of the brief checks exactly this: five values per line, valid class ids, coordinates inside 0 to 1, and a label file for every image.

3Grid cells and scales

What you see

The highlighted cell is the one containing the vehicle’s centre point. Switching scale changes the cell size.

The idea

The grid decides which cell is responsible for predicting an object: the one holding its centre. YOLOv9 uses three grid scales. Coarse grids (large cells) suit big, close vehicles; fine grids (small cells) suit small, distant ones. Small objects are where most detectors lose accuracy, because at 640 pixels they cover very few cells.

In your project

If motorbikes or far-away vehicles score poorly, scale and image resolution are the first things to examine in your critical analysis.

What you see

The raw output is a cloud of overlapping boxes with scores. The slider hides weak ones; the checkbox merges duplicates.

The idea

The network proposes thousands of boxes, most of them poor. Two filters clean this up. The confidence threshold drops boxes the model is not sure about. Non-maximum suppression (NMS) keeps only the best of several boxes that overlap on the same object. Note that NMS alone leaves low-score background guesses; the threshold alone leaves duplicates. You need both.

In your project

Evaluation (step 6) uses a very low threshold, about 0.001, so mAP can sweep every score. Visualisation (step 7) uses 0.25 for readable images. Same model, very different pictures.

What you see

The blue prediction overlaps the dashed annotation. The amber area is the overlap, and each square lights up when the overlap clears that threshold.

The idea

IoU (Intersection over Union) is overlap area divided by combined area, from 0 to 1. A prediction with the right class and IoU of at least 0.5 is a true positive; otherwise it is a false positive, and the missed vehicle is a false negative. Precision is true positives over all predictions, and recall is true positives over all real vehicles. mAP@50 uses the lenient 0.5 test, while mAP@50-95 averages ten thresholds up to 0.95, so it rewards tight boxes.

In your project

Loose or inconsistent annotations lower IoU even for good predictions, which is one way label quality shows up in your scores.

What you see

The blue guess moves toward the dashed annotation a little with each update, quickly at first and then more slowly.

The idea

Each update takes a batch of images, predicts boxes, scores them against the annotations (the loss), and nudges the weights to lower it. One epoch is every training image seen once. With 2,297 images and batch size 4 that is about 575 updates per epoch, so roughly 5,750 over 10 epochs. This is fine-tuning: you start from COCO weights, where the backbone already knows edges and vehicle shapes, rebuild the output layers for your classes, and keep training everything on your data. The loss here is simplified; YOLOv9 combines box, class and DFL losses.

In your project

If validation metrics are still rising at epoch 10, the model is under-trained, which justifies “train longer” as an improvement. Compare the curve in results.csv to this flattening shape.

7Class imbalance

■ training instances   ■ detection quality (synthetic)

What you see

Drag the rare class’s example count up. Its detection quality rises, with diminishing returns, while the common classes stay high.

The idea

The quality curve here is a synthetic illustration, not a measurement. The real point is that overall mAP hides weak classes: a dataset dominated by cars can score well overall while rare vehicles do poorly. Rare classes also have few test examples, so their metrics are statistically fragile. Visually similar classes add confusion, which the confusion matrix reveals.

In your project

Count instances per class in step 2, then explain the per-class results in step 8 using those counts. Remedies to propose: more images of rare classes, targeted augmentation, class re-weighting, or merging classes that annotators cannot reliably tell apart. Label these as proposals to test, not results.
